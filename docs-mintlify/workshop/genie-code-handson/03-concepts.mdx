모듈 3에서 다루는 개념을 초심자 눈높이로 정리합니다. Raw 로그를 신뢰할 수 있는 데이터로 바꾸는 아키텍처와, 그 변환을 선언적으로 자동화·스케줄하는 Databricks 기능을 **무엇 / 왜·언제 / 어떻게**로 설명합니다.

---

### Medallion Architecture (Bronze / Silver / Gold)

- **무엇**: 데이터를 신뢰도에 따라 세 계층으로 쌓는 설계 — **Bronze(원본)** → **Silver(정제·표준화)** → **Gold(비즈니스 집계)**.
- **왜·언제**: 원본을 보존한 채 단계적으로 품질을 높이기 위해서. 상위 계층에서 문제가 생기면 하위 계층에서 다시 만들 수 있어 안전망이 됩니다. 데이터 신뢰성이 필요한 거의 모든 파이프라인의 기본 골격입니다.
- **어떻게**: Bronze는 Raw 로그를 그대로 적재, Silver는 중복 제거·이상치 처리·단위 표준화·참조 무결성 검증으로 정제, Gold는 대시보드·Genie·에이전트·ML이 바로 소비할 수 있게 수율·FPY·OEE·Cpk 등으로 집계합니다.

### Lakeflow SDP (Spark Declarative Pipelines)

- **무엇**: 파이프라인을 SQL/Python으로 "선언"하면 실행 순서·증분 처리·에러 복구를 Databricks가 자동 관리하는 엔진. 이전 이름은 DLT(Delta Live Tables)이며 Lakeflow의 파이프라인 엔진입니다.
- **왜·언제**: 수동 CTAS는 실행 순서를 직접 챙기고 매번 전체를 다시 처리해야 합니다. 변환이 여러 테이블로 늘어나 의존성·증분·재시도를 사람이 관리하기 어려워질 때 SDP로 전환합니다.
- **어떻게**: 테이블 간 의존성은 SDP가 DAG로 자동 해석합니다. Bronze→Silver는 증분 처리하는 **Streaming Table**로, Silver→Gold는 자동 리프레시되는 **Materialized View**로 구성합니다. UI의 Pipelines 메뉴에서 의존성과 품질 상태를 DAG로 시각화할 수 있습니다.

### Expectations (데이터 품질 강제)

- **무엇**: SDP 안에서 데이터 품질 규칙을 선언하는 기능. `expect("규칙명", "조건")` 형태로 위반 레코드를 감지합니다.
- **왜·언제**: 품질 검사를 코드 곳곳의 필터로 흩어 두지 않고, 파이프라인 정의에 규칙으로 못 박아 위반을 자동 추적·리포트하고 싶을 때.
- **어떻게**: 위반 처리 정책을 목적에 맞게 고릅니다 — `expect`(경고만, 통과), `expect_or_drop`(위반 레코드 제거·격리), `expect_or_fail`(위반 시 파이프라인 중단). 워크샵에서는 Silver에 `expect_or_drop`, Gold에 `expect_or_fail`을 적용해 나쁜 데이터가 상위로 올라가지 못하게 막습니다. 실행 후 테이블별 통과율을 확인합니다.

### Quarantine 패턴

- **무엇**: 품질·규칙·참조 무결성 위반 레코드를 버리지 않고 별도의 `quarantine` 스키마로 **분리 보관**하는 패턴.
- **왜·언제**: 오염 데이터를 그냥 삭제하면 왜 걸러졌는지 추적할 수 없고, 반대로 그대로 두면 조인 손실·집계 왜곡을 일으킵니다. 두 문제를 동시에 피하려 할 때.
- **어떻게**: 마스터에 없는 `equipment_id`/`material_lot_id`, 시간 역전 쌍, 비즈니스 규칙 위반(예: `defect_flag=false`인데 `defect_type` 존재) 같은 레코드를 `quarantine`의 전용 테이블로 분리합니다. 나중에 원인 분석·재처리 대상으로 되짚어 볼 수 있습니다.

### Lakeflow Jobs (스케줄 · 트리거 · 재시도)

- **무엇**: 노트북·파이프라인을 스케줄에 맞춰 자동 실행하는 오케스트레이션 기능. 매일 새벽 리프레시 같은 무인 운영을 담당합니다.
- **왜·언제**: 파이프라인을 사람이 매번 눌러 실행하지 않고, 정해진 시각에 자동으로 돌리고 실패에 대비한 안전장치가 필요할 때.
- **어떻게**: cron 스케줄(예: 매일 오전 6시 KST), **재시도**(횟수·간격), **실패 시 이메일 알림**, **타임아웃**을 함께 설정합니다. cron 외에도 연속 실행·파일 도착 트리거·수동 트리거로 시작할 수 있어 상황에 맞게 고릅니다.

### Triggered vs Continuous

- **무엇**: 파이프라인 실행 방식의 두 모드 — **Triggered**(요청 시 한 번 돌고 종료)와 **Continuous**(계속 떠서 새 데이터를 실시간 처리).
- **왜·언제**: 배치 리프레시로 충분하면 Triggered, 지연을 최소화한 실시간성이 필요하면 Continuous를 씁니다.
- **어떻게**: Triggered는 실행할 때만 컴퓨트를 띄워 비용이 낮아 실습·일 단위 갱신에 적합합니다. Continuous는 컴퓨트를 상시 유지하므로 비용이 늘지만 최신성이 높습니다. 워크샵에서는 Triggered를 기본으로 두고 설정 위치만 확인합니다.

### Serverless vs 클래식 컴퓨트

- **무엇**: 파이프라인·Job을 돌릴 컴퓨트를 Databricks가 자동 관리하는 **Serverless**로 쓸지, 사용자가 직접 구성하는 **클래식 컴퓨트**로 쓸지의 선택.
- **왜·언제**: 기동이 빠르고 관리가 필요 없는 게 우선이면 Serverless, 노드 타입·워커 오토스케일·Photon 사용까지 세밀히 잡아 비용/성능을 튜닝해야 하면 클래식.
- **어떻게**: Serverless에서는 오토스케일·Photon 같은 옵션이 자동 처리됩니다. 클래식에서는 워커 min/max, 노드 타입, Photon 여부를 직접 지정합니다. 초기엔 Serverless + Triggered가 편하고, 운영 요건이 구체화되면 클래식으로 전환합니다.

## 요약

| 개념 | 한 줄 정의 | 이 워크샵에서의 쓰임 |
|------|-----------|--------------------|
| Medallion | Bronze→Silver→Gold 신뢰도 3계층 | Raw 로그를 단계적으로 정제·집계 |
| Lakeflow SDP | 선언하면 순서·증분·복구 자동 관리 | 수동 CTAS를 선언적 파이프라인으로 전환 |
| Expectations | 파이프라인 내 품질 규칙 선언 | 위반 자동 감지·격리·중단 |
| Quarantine | 위반 레코드를 삭제 대신 분리 보관 | 조인 손실·왜곡 방지 + 추적 가능 |
| Lakeflow Jobs | 파이프라인 스케줄·자동 실행 | 매일 새벽 무인 리프레시 |
| Triggered vs Continuous | 단발 배치 vs 상시 실시간 | 비용·최신성 트레이드오프 선택 |
| Serverless vs 클래식 | 자동 관리 vs 직접 튜닝 컴퓨트 | 편의성 vs 세밀한 비용/성능 제어 |
