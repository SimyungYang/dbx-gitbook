모듈 1에서는 카메라 모듈 공장의 원천 로그(Bronze 17테이블, 약 250만 건)를 준비합니다. 여기서 만나는 기술 — **합성/시드 데이터**, **PySpark**, **Faker·dbldatagen**, **Delta Lake**, **Parquet**, **임포트(COPY INTO·CTAS)**, **UC Volumes**, 그리고 **의도적 데이터 품질 이슈** — 를 정리합니다.

### 합성 데이터 / 시드 데이터

- **무엇** — 실제 운영 데이터 대신, 있을 법한 분포·상관관계를 흉내 내어 만든 가짜 데이터. 강사가 미리 만들어 공유하는 것을 **시드(seed) 데이터**라고 부른다.
- **왜/언제** — 실제 제조 데이터는 민감하고 구하기 어렵다. 교육·데모·테스트에서는 진짜처럼 생긴 데이터가 필요하되, 개인정보·기밀이 없어야 한다. 40명이 동시에 각자 생성하면 시간·편차·Rate Limit 문제가 생기므로, 워크샵은 강사가 만든 **동일 시드 데이터 임포트**를 기본으로 한다.
- **어떻게(핵심)** — 이 워크샵은 두 트랙을 병행한다. (A) 강사가 만든 시드 데이터를 **임포트**해 이후 모듈 결과를 재현 가능하게 하고, (B) Genie Code로 직접 **생성**하는 과정을 시연해 원리를 이해한다.

### PySpark

- **무엇** — 대규모 데이터를 여러 노드에 나눠 병렬 처리하는 분산 엔진 Spark의 Python API.
- **왜/언제** — 수십만~수백만 건을 한 대의 메모리로 다루기 어려울 때. 이 워크샵은 250만 건을 만들고 저장하므로 병렬 처리가 자연스럽다. Serverless 제약 때문에 pandas 대신 PySpark를 기본으로 쓴다.
- **어떻게(핵심)** — 데이터를 DataFrame으로 표현하고, 실제 연산은 저장·집계 같은 액션 시점에 병렬 실행된다. Genie Code가 프롬프트를 받아 PySpark 생성 코드를 자동으로 작성한다.

### Faker / dbldatagen

- **무엇** — 현실적인 가짜 값을 만들어 주는 라이브러리. Faker는 이름·날짜·코드 같은 개별 값 생성에, `dbldatagen`은 분포·상관관계를 제어한 대량 생성에 강하다.
- **왜/언제** — "설비 300대, status는 RUNNING 80%/IDLE 10%…" 같이 분포·비율을 지정한 데이터가 필요할 때. 단순 난수보다 통제된 현실성을 얻는다.
- **어떻게(핵심)** — 컬럼별 분포·범위·상관 규칙을 지정하면 그 규칙에 맞는 대량 레코드를 만든다. Serverless에서는 `%pip install faker`로 설치해 쓴다.

### Delta Lake

- **무엇** — Databricks의 기본 테이블 형식. Parquet 파일 위에 트랜잭션 로그를 얹어 안정성과 이력 관리를 더한 오픈 포맷이다.
- **왜/언제** — 데이터를 쓰는 도중 실패하거나 여러 작업이 겹쳐도 테이블이 깨지지 않아야 할 때, 그리고 "어제 상태로 되돌려 보고 싶을" 때.
- **어떻게(핵심)** — 두 가지가 핵심이다.
  - **ACID 트랜잭션** — 쓰기가 전부 반영되거나 전부 취소된다(중간 상태 없음). 동시 읽기·쓰기에도 일관성이 유지된다.
  - **Time Travel** — 트랜잭션 로그가 버전을 남기므로 특정 시점·버전의 테이블을 다시 조회할 수 있다.
  - 이 워크샵은 모든 테이블을 Delta로 저장하고 `CREATE OR REPLACE TABLE`로 안전하게 덮어쓴다.

### Parquet

- **무엇** — 컬럼 단위로 압축·저장하는 오픈 파일 포맷. Delta Lake의 실제 데이터도 내부적으로 Parquet로 저장된다.
- **왜/언제** — 분석 쿼리는 대개 일부 컬럼만 읽는다. 컬럼 저장은 필요한 컬럼만 읽어 스캔량을 줄이고 압축률도 높다. 시드 데이터를 시스템 간에 주고받는 교환 포맷으로도 쓴다.
- **어떻게(핵심)** — 강사는 시드 데이터를 테이블별 parquet 폴더로 공유 볼륨에 올려두고, 참가자는 그 폴더를 읽어 Delta 테이블로 적재한다.

### 임포트 — COPY INTO / CTAS

- **무엇** — 외부에 있는 데이터를 내 테이블로 적재하는 두 방식. **COPY INTO**는 파일(Parquet 등)을 테이블로 반복 적재하고, **CTAS**(`CREATE TABLE AS SELECT`)는 쿼리 결과를 그대로 새 테이블로 만든다.
- **왜/언제** — 공유 볼륨의 parquet을 Delta 테이블로 올릴 때는 파일 적재형(COPY INTO 또는 파일을 읽어 저장), Delta Sharing·Marketplace로 공유된 카탈로그를 복제할 때는 CTAS가 자연스럽다.
- **어떻게(핵심)** — 이 워크샵의 임포트 트랙은 parquet 폴더 17개를 읽어 동일 이름의 Delta 테이블로 `CREATE OR REPLACE TABLE` 저장하거나, 공유 카탈로그를 CTAS로 복제한다. 완료 후 row count와 참조 무결성을 검증한다.

### Unity Catalog Volumes

- **무엇** — Unity Catalog 스키마에 속한, 파일을 담는 저장 영역. 테이블(정형)과 달리 PDF·이미지·parquet 폴더 같은 파일을 거버넌스 아래 둔다.
- **왜/언제** — DBFS 마운트가 막힌 Serverless 환경에서 파일을 다룰 때의 표준 경로. 시드 데이터 공유, 이후 모듈의 비정형 파일 저장에 쓴다.
- **어떻게(핵심)** — `/Volumes/<catalog>/<schema>/<volume>/` 경로로 접근한다. 공유 시드는 예컨대 공유 볼륨 경로 아래 테이블별 parquet 폴더로 배치된다.

### 의도적 데이터 품질 이슈 (교육적 목적)

- **무엇** — 시드 데이터에 일부러 심어 둔 결함. 중복·시간 역전, 단위 오류(µm↔mm로 1000배), 규칙 위반(`defect_flag=false`인데 불량코드 존재), 결측(구형 테스터의 NULL), 이상치(`mtf_center_pct > 100`) 등.
- **왜/언제** — 실제 제조 데이터는 결코 깨끗하지 않다. 완벽한 데이터로는 이후 모듈의 EDA·품질 진단·정제·AI 함수 실습이 성립하지 않는다. 그래서 현실의 지저분함을 재현한다.
- **어떻게(핵심)** — 자재 로트↔불량, 설비 노후↔고장 전조, 환경 파티클↔오염 불량처럼 **분석으로 찾아낼 수 있는 상관**과 함께 결함을 심는다. 이후 모듈에서 "심어 둔 이슈를 실제로 잡아내는지"를 검증한다.

> MDX 참고: 스키마 표에 나오는 `MAP<STRING,STRING>`·`ARRAY<STRING>` 같은 타입은 백틱으로 감싸 표기한다.
