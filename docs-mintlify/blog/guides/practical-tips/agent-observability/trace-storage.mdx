---
title: "Trace 저장 — Experiment vs Unity Catalog"
---

<Note>
  Trace를 만드는 방법은 [MLflow Tracing](/blog/guides/practical-tips/agent-observability/mlflow-tracing)을, Unity Catalog로 전송하는 구현은 [OTel → UC 전송](/blog/guides/practical-tips/agent-observability/otel-to-uc)을 참고하세요.
</Note>

MLflow Trace는 두 곳에 저장할 수 있습니다. 개발 단계에서는 MLflow Experiment에 저장하고, 운영 단계에서는 Unity Catalog에 저장합니다. 목적이 다르므로 선택 기준을 먼저 정리합니다.

## 두 저장 방식 비교

| 항목 | MLflow Experiment 저장 (개발) | Unity Catalog 저장 (운영) |
| --- | --- | --- |
| 설정 | 간단 | SQL Warehouse·권한 설정 필요 |
| Trace 개수 | **Experiment당 최대 100,000개 제한** | **무제한** |
| SQL 분석 | 불가 (OTel client 호환 저장소 아님) | 가능 |
| 권한 제어 | 제한적 | catalog/schema/table 단위 제어 |
| 장기 보존 | 제한적 | 지원 |
| 상태 | — | **2026년 7월 GA** |

## UC 저장 구조

Unity Catalog에 저장하면 지정한 catalog/schema 아래에 OTel 형식 Delta 테이블이 생성됩니다. 테이블 이름은 지정한 prefix로 시작합니다.

```text
Unity Catalog
└── catalog.schema
    ├── <prefix>_otel_spans
    ├── <prefix>_otel_logs
    ├── <prefix>_otel_metrics
    └── <prefix>_otel_annotations
```

`_otel_spans`에는 span 트리가, `_otel_logs`에는 로그가, `_otel_metrics`에는 메트릭이, `_otel_annotations`에는 평가·라벨 같은 부가 정보가 담깁니다.

## 언제 무엇을 쓸까

- **개발·디버깅**: MLflow Experiment 저장. 설정이 간단하고 바로 UI에서 Trace를 확인할 수 있습니다.
- **프로덕션**: Unity Catalog 저장. Trace 개수 제한이 없고 SQL로 분석하며 권한과 보존을 catalog 단위로 관리합니다.

프로덕션에서 Unity Catalog로 Trace를 전송하는 구체적 구현은 [OpenTelemetry SDK로 Unity Catalog에 전송하기](/blog/guides/practical-tips/agent-observability/otel-to-uc)에서 다룹니다.
